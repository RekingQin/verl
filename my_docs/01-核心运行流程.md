# 01 · 核心运行流程（数据流 / 控制流 / 分布式架构）

> 返回索引：[README.md](README.md)

## 1.1 设计哲学：HybridFlow 单控制器（Single-Controller）

verl 源自论文 *HybridFlow: A Flexible and Efficient RLHF Framework*。其核心思想是：

- **单控制器（Single Controller）+ 多工作者（Multi-Worker）**：一个 Driver 进程（Python 主程序）以"近似单机"的命令式代码编排整个 RL 数据流；而所有重型计算（训练 / 推理生成）下沉到 Ray 管理的 Worker 集群中执行。
- **计算与数据依赖解耦**：Driver 只负责"控制流"（先 rollout、再算 logprob、再算 advantage、再 update），具体"数据如何在多卡间切分/聚合"由 `@register(dispatch_mode=...)` 装饰器声明，框架自动完成 dispatch/collect。

这使得新增一个 RL 算法（GRPO/PPO/...）只需在 Driver 层写几十行编排逻辑，而无需关心底层 3D 并行细节。

## 1.4 控制流：一个训练 step（`PPOTrainer.step`，trainer/ppo/v1/trainer_base.py:509）

```
 fit() 循环 (epoch -> dataloader batch; fit @ trainer_base.py:387):
 ┌──────────────────────────────────────────────────────────────────────────┐
 │ step(batch): (:509)                                                       │
 │                                                                            │
 │ (1) 生成 uid，put 到 AgentLoopManager（非阻塞 fire-and-forget）            │
 │      agent_loop_manager.generate_sequences(batch)                          │
 │           │   AgentLoopWorkerTQ 为每个 prompt 起 n 个异步 agent loop       │
 │           │   完成后把输出写入 TransferQueue (key={uid}_{session}_{idx})   │
 │           v                                                                │
 │ (2) gen: replay_buffer.sample(global_steps) 阻塞等待该 step 全部 prompt    │
 │      完成 -> 返回 KVBatchMeta（仅元数据，不搬运张量）                       │
 │           v                                                                │
 │ (3) [可选] reward: colocate reward model 打分                              │
 │ (3') REMAX: 追加 greedy baseline reward                                    │
 │           v                                                                │
 │ (4) _balance_batch: 按 seqlen 负载均衡重排 (:1453)                         │
 │           v                                                                │
 │ (5) old_log_prob: actor_rollout_wg.compute_log_prob(batch)                 │
 │           v                                                                │
 │ (6) [可选] ref: ref_policy_wg.compute_ref_log_prob (或 ref_in_actor)       │
 │ (7) [可选] values: critic_wg.infer_batch                                   │
 │           v                                                                │
 │ (8) adv: apply_kl_penalty -> rollout_correction -> compute_advantage       │
 │           v                                                                │
 │ (9) [可选] update_critic (:1649)                                           │
 │ (10) update_actor (:1672; critic_warmup 之后)                              │
 └──────────────────────────────────────────────────────────────────────────┘
       │
       ├─> save_checkpoint (按 save_freq)
       ├─> checkpoint_manager.update_weights()  # trainer 权重 -> rollout 引擎
       ├─> _validate (按 test_freq)
       └─> _compute_metrics + log + tq.kv_clear / replay_buffer.remove
```

要点：
- **为什么 step1 已 generate，step2 还要 sample？** `generate_sequences` 是 **fire-and-forget 非阻塞**，签名 `-> None`，根本不返回生成结果。它只做两件事：① 把本 step 所有 uid 在 ReplayBuffer 标记为 `running`；② 把 prompt 派发给 AgentLoopWorker，后者起一堆 `asyncio` 后台任务就立刻返回（`ray.get` 只等"派发完成"，不等"生成完成"）。真正的结果由各 worker **异步**写入 TransferQueue。`sample(global_steps)` 才是**同步屏障 + 结果筛选**：阻塞轮询直到本 step 所有 prompt 状态非 `running`，再把 `success` 的 key 打包成 `KVBatchMeta` 返回。拆成两步是为了 fire-and-forget 流水线 + on-policy 同步语义（本 step 训练数据必须来自本 step rollout）。rollout 高度不规整（每 prompt 起 n session、可能多轮、变长、可能失败），所以"点火"与"收口对齐"必须分离。
- **每个 `_compute_*` 方法的统一范式**：`tq.kv_batch_get`（取所需字段）→ 计算 → `tq.kv_batch_put`（写回结果），全程只在 Worker 内做张量计算，Driver 只过元数据 `KVBatchMeta`。
- **old_log_prob 的两种模式**（`_compute_old_log_prob`，trainer_base.py:1479）：
  - *bypass 模式*：直接令 `old_log_probs = rollout_log_probs`（2 策略 π_rollout / π_θ）。
  - *decoupled 模式*：重算 old_log_probs 作为稳定锚（3 策略 π_rollout / π_old / π_θ），用于 rollout 修正（IS 权重、拒绝采样）。

## 1.5 数据流：TransferQueue 数据面

```
 [Dataset] --collate--> batch_dict --get_tensordict--> TensorDict(prompt)
      |                                                       |
      | generate_sequences(非阻塞)                            v
      |                                          +-----------------------+
      |                                          | AgentLoopWorkerTQ      |
      |                                          |  - 调 LLMServer 生成   |
      |                                          |  - 调 reward 打分      |
      |                                          |  - tq.async_kv_put     |
      |                                          +-----------+-----------+
      |                                                      | 写入(key->fields,tags)
      v                                                      v
 +---------------------+   poll(1s)   +--------------------------------------+
 | ReplayBuffer        | <----------- |       TransferQueue (tq)             |
 | partitions[part_id] |              |  key={uid}_{sid}_{idx}               |
 |  ={key:{status,...}}|  sample()    |  fields=nested TensorDict(变长序列)  |
 +----------+----------+ -----------> |  tags={global_steps,status,seq_len}  |
            |  KVBatchMeta(keys,tags) +--------------------------------------+
            v                                    ^   ^
   Driver 编排各计算阶段                          |   |  kv_batch_get/put
   (只传 keys/tags, 不搬张量) --------------------+---+
```

`ReplayBuffer`（`verl/trainer/ppo/v1/replay_buffer.py`，自原 main_ppo_sync.py 迁移而来）后台线程每 `poll_interval` 轮询 TransferQueue 元数据；`sample(global_steps=...)` 会阻塞直到该 step 所有 prompt 状态非 `running`，从而实现"同步采样"语义。变长序列以 nested tensor 存储，避免全局 padding（零填充 / 零拷贝即来源于此）。

**关键澄清：ReplayBuffer 不存张量，只存元数据索引。** 数据并非"从 TQ 搬到 ReplayBuffer"：
- AgentLoopWorker 把**张量本体 fields + 元数据 tags** 一起 `async_kv_batch_put` 进 TransferQueue（张量从此一直留在 TQ）。
- ReplayBuffer 后台线程每秒只 `tq.kv_list()` 拉**元数据**（key→tags，含 `global_steps/status/seq_len`），构建一份"哪些 key 已就绪/属于哪个 step/状态如何"的轻量索引，用于同步协调。
- `sample()` 返回 `KVBatchMeta`（**只有 keys+tags，不含张量**）：① 等本 step 全部完成的屏障；② 筛出 `success` 的 key。
- 训练真正用数据时，各计算阶段在 **Worker 内部**用这些 key 去 TQ `kv_batch_get` 取张量 → 计算 → `kv_batch_put` 写回；Driver 全程只传 `KVBatchMeta`，张量不经 Driver（零拷贝数据面）。

```
AgentLoopWorker --(张量+元数据)--> TransferQueue(真正存张量)
                                       │ 每秒只拉元数据
                                       ▼
                                  ReplayBuffer(只是元数据索引/同步器)
                                       │ sample() 返回 KVBatchMeta(keys+tags)
                                       ▼
                 各计算阶段在 Worker 内 kv_batch_get 直接从 TQ 取张量训练
```

## 1.6 分布式调度：dispatch / collect 机制（详解）

核心目标：让 Driver 用"近似单机"的命令式代码 `wg.compute_log_prob(batch)` 调用，框架在背后自动完成"数据如何切分到各 GPU rank、并发执行、再聚合回来"。整条链路分四个阶段：

### (1) 声明期：`@register`
Worker 方法用 `@register(dispatch_mode, execute_mode, blocking)` 装饰（`decorator.py:398`），把这三个属性写进方法的 `MAGIC_ATTR`：

```python
# decorator.py（MAGIC_ATTR = "attrs_3141562937" @ :23，写属性 @ :398 附近）
attrs = {"dispatch_mode": dispatch_mode, "execute_mode": execute_mode, "blocking": blocking}
setattr(wrapper, MAGIC_ATTR, attrs)
```

注意 `register` 内部还套了一层 `func = tqbridge(dispatch_mode=...)(func)`（decorator.py:425）——这是同步链路衔接 TransferQueue 的关键（见第 (5) 点）。

### (2) 绑定期：`_bind_worker_method` + `func_generator`
构造 WorkerGroup 时，`_bind_worker_method`（worker_group.py:185）扫描所有带 `MAGIC_ATTR` 的方法，用 `func_generator`（ray/base.py:49）在 WorkerGroup 上动态生成同名代理方法。代理本质是个 `Functor`：

```python
# ray/base.py:50
class Functor:
    def __call__(this, *args, **kwargs):
        args, kwargs = dispatch_fn(self, *args, **kwargs)   # ① 切分
        output = execute_fn(method_name, *args, **kwargs)   # ② 各 rank 并发 .remote()
        if blocking: output = ray.get(output)               # ③ 可选阻塞
        output = collect_fn(self, output)                   # ④ 聚合
        # ⑤ 去除 padding 补齐的样本
```

### (3) 三个可插拔函数（由 dispatch_mode 决定）
- **dispatch_fn**：把 Driver 的整批数据切给各 rank。以最常用的 `DP_COMPUTE_PROTO` 为例（`dispatch_dp_compute_data_proto`，decorator.py:167），会**先 auto-padding 到能被 world_size 整除**，再 `chunk(world_size)`。
- **execute_fn**：向各 rank 的 Ray actor 发 `.remote()` 并发执行。
- **collect_fn**：`DP_COMPUTE_PROTO` 用 `concat`（`collect_dp_compute_data_proto`，decorator.py:191）把各 rank 结果拼回；最后 `func_generator` 再把第 (3) 步 padding 补的样本切掉。

### (4) 预定义 Dispatch 模式（`init_predefined_dispatch_mode`，decorator.py:38）
- `ONE_TO_ALL`：同一参数广播给所有 rank（如初始化）。
- `ALL_TO_ALL`：原样透传。
- `DP_COMPUTE_PROTO`：按数据并行（DP）维度把 `DataProto`/batch 均分到各 DP rank，结果再 `concat` 回来（最常用于 logprob/train）。
- `DP_COMPUTE_PROTO_WITH_FUNC`：附带把函数也一起分发执行。
- `DIRECT_ROLLOUT_METHOD`：vLLM external executor 专用。

`execute_mode`（`Execute`）控制 `ALL`（所有 rank 执行）或 `RANK_ZERO`（仅 0 号）。

### (5) 与同步链路衔接：tqbridge
因为 `register` 套了 `tqbridge`，同步链路里 Driver 传递的是 `KVBatchMeta`（元数据句柄），dispatch 切的也是"句柄"，而真正的张量取用（`kv_batch_get`）/写回（`kv_batch_put`）发生在 **Worker 内部**，张量不经 Driver。这与 1.5 节的零拷贝数据面是同一回事。

### (6) 资源与拓扑
- `ResourcePoolManager`（ray/base.py:185）经 Ray PlacementGroup 分配资源；默认所有角色共享 `global_pool`，reward/teacher 可独立成池。
- Worker 启动时从环境变量读 `WORLD_SIZE/RANK/MASTER_ADDR/MASTER_PORT` 建 torch.distributed（NCCL/HCCL）通信组（`worker.py:181` `__init__`）。
- `_balance_batch`（trainer_base.py:1453）在按 seqlen 重排前，会先 `_query_dispatch_info` 拿 actor 的 DP size，保证重排后的全局 batch 能被 `dispatch_fn` 整除均分。
