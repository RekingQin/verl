### ESI 抢占检测（`should_save_ckpt_esi`，checkpoint_manager.py:259）

**ESI = Elastic Server Instance（弹性 / 抢占式算力实例）**。这类按"容量块（capacity block）"租用的云算力有明确的到期/可能被回收时间点，到点后实例可能被平台强制抢占。该函数用于"**抢占前主动落盘**"判断：

```
 读取容量到期时间戳（环境变量，平台二选一）：
   - MLP_CURRENT_CAPACITY_BLOCK_EXPIRATION_TIMESTAMP        # 火山引擎 vemlp
   - SAGEMAKER_CURRENT_CAPACITY_BLOCK_EXPIRATION_TIMESTAMP  # AWS SageMaker

 remaining = 到期时间 - 现在
 若 remaining <= save_ckpt_duration + max_steps_duration + redundant_time
     => 返回 True（再跑一步可能来不及存盘，应立即保存 ckpt）
```

参数：`max_steps_duration`（单步最大估计耗时）、`save_ckpt_duration`（存 ckpt 估计耗时，默认 60s）、`redundant_time`（缓冲冗余，默认 0）。
目的：在实例被回收前的安全窗口内强制存盘，避免抢占瞬间丢失整个 step 进度。对应的进阶方向见 [09-后续优化Todo指引.md](09-后续优化Todo指引.md) 的「细粒度抢占恢复」（在 step 边界判断之外，做到步内安全点）。

## 4.2 权重同步引擎（`verl/checkpoint_engine/`）

解决的核心问题：训练侧（FSDP/Megatron/VeOmni…，简称 ME=Model Engine）更新完权重后，要把最新权重高效灌给推理侧（vLLM/SGLang rollout 引擎，简称 CE=Checkpoint Engine），且要支持 colocate / 分离 / 异构 / 弹性等多种拓扑。

### 统一抽象（`CheckpointEngine`，checkpoint_engine/base.py:96）

通过 `@CheckpointEngineRegistry.register(backend)`（base.py:49）注册，五个抽象接口构成一次同步的生命周期：

```
 prepare()        # 分配权重 bucket；[可选]为 RDMA 注册；返回建组元数据(master ip:port / RDMA desc)
   |
 build_topology(trainer_ws, rollout_ws, metadata)   # 汇总各 worker 元数据，算出通信拓扑
   |
 init_process_group(**kwargs)                        # 按拓扑建 trainer+rollout 联合通信组
   |
 send_weights(generator)  /  receive_weights()       # 逐 tensor 流式收发(生成器, 边发边收)
   |
 finalize()       # 释放 bucket；[可选]注销 RDMA / 销毁进程组
```

- **流式分块**：`split_weight_chunks` / `merge_weight_chunks`（base.py:541/570）按 `update_weights_bucket_megabytes` 把大张量切成 bucket，避免一次性占满显存，发送端切、接收端按 `TensorMeta(name/shape/dtype/chunk_offset/chunk_size)` 重组。
- **CheckpointEngineWithCache**（base.py:208）：带本地缓存（shm/disk）的变体，可在不打断 rollout 在途请求（partial rollout）的前提下同步权重，请求耗尽后再从本地缓存取（Laminar，arXiv:2510.12633）。
- **trainer/rollout 进程关系**：trainer 侧 ME 与 CE 同进程；rollout 侧 CE 与 rollout worker 分进程，经 **CUDA IPC** 传权重（见 base.py 的拓扑图）。

### 后端选型（`checkpoint_engine/README.md`）

| 后端 | 通信库 | 拓扑 | 弹性 | 典型场景 |
|------|--------|------|------|----------|
| `naive` | torch.distributed | all_gather | — | **on-policy，trainer/rollout colocate**（默认，`ColocatedCheckpointEngine` base.py:226） |
| `nccl` | NCCL | all_gather+broadcast | 低(需重建组) | off-policy，分离部署，固定集群 |
| `hccl` | HCCL | all_gather+broadcast | 低 | Ascend NPU 分离部署 |
| `nixl` | NIXL(UCX/UCCL/Mooncake) | all_gather+ring p2p | **高(动态调 ring)** | 弹性 rollout / rollout 容错 / 异构硬件 |
| `mooncake` | Mooncake Transfer Engine | all_gather+ring p2p | 高 | 分离部署 |
| `kimi_ckpt_engine` | Mooncake+NCCL/HCCL | p2p+broadcast | 低 | 分离部署 + 每次存 ckpt |
| `delta`（新增） | NCCL（`ray.util.collective`） | sparse broadcast（字节级 diff） | 中 | 分离 rollout 的**增量权重同步**：训练端对 pinned-CPU 快照做 diff，只广播变化的稀疏 `(position, value)` 对，rollout 端经 SGLang `--custom-weight-loader` 原位 masked-apply（`delta_checkpoint_engine.py::DeltaShardedCheckpointEngine`） |

### `CheckpointEngineManager`（checkpoint_engine/base.py:361）协调流程

`update_weights(global_steps)`（base.py:486）的完整步骤（非 naive 路径）：
1. `abort_replicas`（:458）：中止并保存所有 rollout 在途请求（支持 partial rollout）。
2. 把所有 replica 的 worker 临时组成一个 `RayWorkerGroup`。
3. `release_kv_cache_replicas`（:468）：只释放 KV cache、**保留权重 buffer**，让 NCCL 直接写入原地。
4. `build_process_group`（:403）：`prepare`(各 worker) → `build_topology` → `init_process_group`。
5. trainer `send` + rollout `receive` 并发执行权重同步。
6. `finalize` 各 worker。
7. `resume_kv_cache_replicas`（:478）+ `resume_generation_replicas`（:463）：恢复 KV cache 与在途请求。

> naive 路径（colocate）走捷径：直接 `trainer.update_weights(mode="naive")` 一步完成（`ColocatedCheckpointEngine`，base.py:226）。
> 弹性接口：`add_replicas`（:430）/ `remove_replicas`（:438）增删 replica 后会重建进程组（配合 nixl/mooncake 的高弹性）。
> `sleep_replicas`（:448）/ `wake_up_replicas`（:453）：训练阶段让 rollout 引擎释放权重+KV 显存（见 [05-性能优化设计.md](05-性能优化设计.md)）。

`CheckpointEngineManager` 在 `PPOTrainer.init()`（trainer_base.py:217）中创建（:358）；每个 step 末尾由 `checkpoint_manager.update_weights()` 触发权重刷新（`PPOTrainerSync.on_step_end`）。

### 4.2.1 为什么权重同步时只 offload/resume KV cache，不动权重？

`update_weights` 第 3 步用的是 `release_kv_cache_replicas`（"只释放 KV、保留权重 buffer"），而不是 `sleep_replicas`（释放权重+KV）。三点原因：

1. **权重 buffer 要原地接收（in-place）**：NCCL/CUDA-IPC 同步时，新权重直接**写入 rollout 引擎已有的权重显存 buffer**，所以这块 buffer 必须保留——释放了就没地方原地写、还得重新分配，反而更慢。
2. **腾显存给同步过程**：权重同步需要额外缓冲（bucket 收发 buffer，NCCL engine 用 `2 * bucket_size`）。KV cache 占用大且此刻无用，释放它腾空间是性价比最高的选择。
3. **KV cache 本就该丢弃**：权重一换，基于旧权重算出的 KV cache 在数值上即失效，本来就要清空（`resume_kv_cache` 后还会 `flush_cache`），所以"释放→同步→恢复"对 KV 无正确性损失。

对比：`sleep_replicas` 用于**训练阶段**（colocate 下整卡让给 trainer，代价是事后要重灌权重）；`release_kv_cache` 用于**权重同步阶段**（轻量，保留权重 buffer 供原地写）。LoRA adapter 模式（`lora_as_adapter`）更极端——只释放 KV cache，base 权重全程留卡，仅同步 adapter delta（async_sglang_server.py:470）。

## 4.3 进程级容错

verl 的进程级容错由"**后台心跳监控 + 信号通知主线程 + 拓扑稳定保证**"三部分组成。

### 机制一：worker 存活监控（`worker_group.py:102`）

```
 start_worker_aliveness_check(every_n_seconds=1):
   ① _block_until_all_workers_alive()      # 先阻塞等所有 worker 就绪
   ② 起 daemon 线程跑 check_workers_alive:  # 持续轮询
        while True:
          for w in workers:
            if not is_alive(w):             # Ray: 查 actor state != "ALIVE"
              signal.raise_signal(SIGABRT)  # 向主线程发 SIGABRT，触发整体退出
          sleep(every_n_seconds)
```

`_is_worker_alive`（Ray 实现，ray/base.py:499）通过 `get_actor(actor_id)["state"] == "ALIVE"` 判断 actor 是否存活。一旦任一 worker 进程崩溃，监控线程立即给 Driver 主进程发 `SIGABRT`——**fail-fast**：与其让 Driver 卡在已死 worker 的 `ray.get` 上无限等待，不如让整个 job 快速失败退出，再由外层调度（K8s/Ray `max_restarts` 等）拉起，并从最新 checkpoint（4.1）恢复。这是"崩溃即重启 + ckpt 续训"的容错闭环。

### 机制二：拓扑稳定保证（`sort_placement_group_by_node_ip`，ray/base.py:70）

按 node ip 对 PlacementGroup 排序（在 `get_placement_groups`，ray/base.py:131 调用），保证多次 Ray job / 集群重启后 RANK 与物理节点稳定对应——这样 FSDP 的分片 ckpt（`rank_{r}.pt`）才能在 resume 时被正确的 rank 读回。

**注意区分两个层面**（这点容易混淆）：

- **(A) RANK↔节点稳定**：解决的是"**整个 job 重启后续训可复现**"，**不是**运行中热加入。崩溃时是整个 job fail-fast 退出，再重新拉起、重排序、按上次拓扑重建。
- **(B) 新 rollout replica 运行中"加入通信组"**：这才是动态扩缩，机制在**权重同步引擎层**（NCCL engine 的 `rebuild_group` + 每 step 重建拓扑，`nccl_checkpoint_engine.py`）：
  - 每次 `CheckpointEngineManager.update_weights` 都 `build_process_group`（`prepare → build_topology → init_process_group`）。
  - trainer rank0 是唯一 src（其余 trainer rank 标 `rank=-1` 只消费不发）；rollout 各 worker 占 `rank=1..rollout_ws`，联合 `world_size = rollout_ws + 1`。
  - master（trainer rank0）开 **zeromq PUB** 广播 bucket 元数据，新加入的 rollout worker 作为 **SUB** 经 `prepare` 拿到 master 的 `zmq ip:port` 连上来；张量本体走 **NCCL broadcast(src=0)**。
  - **新节点入组流程**：`add_replicas` 登记新 replica → 下次 `update_weights` 时 `build_topology` 把新 worker 的 rank/world_size 算进去 → `init_process_group`（`rebuild_group=True` 时 `collective.init_collective_group` 重建组）→ SUB 连 master、`collective.barrier` 对齐 → 入组完成。
  - **弹性程度由后端决定**：nccl/hccl 需整组重建（弹性低）；nixl/mooncake 用 ring p2p 拓扑可低成本动态调整（弹性高，见 4.2 后端表）。

### 示例：如何做到进程级容错（`tests/single_controller/check_worker_alive/main.py`）

```python
@ray.remote
class TestActor(Worker):
    @register(dispatch_mode=Dispatch.ONE_TO_ALL, blocking=False)
    def foo(self, wait_time):
        time.sleep(wait_time)
        sys.exit(1)        # 模拟 worker 进程崩溃

wg = RayWorkerGroup(resource_pool, RayClassWithInitArgs(cls=TestActor), name_prefix="test")
wg.start_worker_aliveness_check(1)   # 开启 1s 间隔的存活监控
wg.foo(wait_time)                    # 非阻塞调用，worker 会在 wait_time 后自杀
time.sleep(wait_time * 6)            # 主进程在此期间会收到 SIGABRT 而中止
```

流程：`foo` 里 `sys.exit(1)` 让某个 worker actor 死亡 → 监控线程下一轮 `_is_worker_alive` 返回 False → `signal.raise_signal(SIGABRT)` → Driver 主进程被 SIGABRT 终止（不会傻等 `foo` 的结果）。在真实训练里，外层重启 + 4.1 的 ckpt resume 即可让训练从上一个 step 边界继续。

> 进阶：`recipe/fault_recover/fault_manager.py` 用 `SIGALRM` + 超时给单个 rollout 任务做更细粒度的超时/故障恢复（捕获 `RayTaskError`/`RayActorError`），可作为步内安全点的参考方向（见 [09-后续优化Todo指引.md](09-后续优化Todo指引.md)）。
