## 1. 先建立一句话心智模型

verl 是一个 **RLHF / RLVR / 强化学习训练框架**，核心范式是 **HybridFlow 单控制器**：

```text
一个 Driver（主进程）像写单机代码一样编排 RL 流程：
    rollout 生成 response
        ↓
    计算 old_log_prob / ref_log_prob / value / reward
        ↓
    计算 advantage / KL penalty
        ↓
    更新 critic
        ↓
    更新 actor
        ↓
    同步 checkpoint / 权重到 rollout engine
        ↓
    进入下一个训练 step

而所有重计算（训练 / 推理 / reward）都下沉到 Ray 管理的 Worker 集群里跑。
```

记住这条主链路，后面所有目录都是围绕它的“零件”：

- **谁来编排？** → `trainer/`（Driver / Trainer）
- **重计算在哪跑？** → `workers/`（Actor / Critic / Ref / Reward / Rollout）
- **Driver 怎么把活派到多卡？** → `single_controller/`（dispatch / collect 调度）
- **数据长什么样、怎么传？** → `protocol.py` + `utils/transferqueue_utils.py`
- **模型怎么适配？** → `models/`
- **算法在哪里？** → `trainer/ppo/core_algos.py`
- **权重怎么保存和同步？** → `utils/checkpoint/` + `checkpoint_engine/`
- **工具调用 / Agent 在哪里？** → `tools/` + `experimental/agent_loop/`

你可以把 verl 看成下面这张图：

```text
examples 脚本 / Hydra 配置
        ↓
trainer 训练入口与训练循环
        ↓
single_controller 单控制器调度
        ↓
workers 远端训练 / 推理 / reward worker
        ↓
engine 训练后端：FSDP / Megatron / VeOmni / TorchTitan / MindSpeed
        ↓
rollout 后端：vLLM / SGLang / TensorRT-LLM / HF / naive
        ↓
protocol / TransferQueue / TensorDict 负责数据封装和传递
```

## 2. 新手阅读原则：不要逐文件硬啃

verl 的代码目录很多，直接从 `utils/` 或某个底层 engine 开始读，很容易迷路。更推荐按“主链路 + 问题驱动”的方式阅读。

### 2.1 推荐总路线

```text
第 0 站：examples/ 中找一个能跑的脚本
    ↓
第 1 站：protocol.py
    理解 DataProto / TensorDict / meta_info 等数据载体
    ↓
第 2 站：trainer/main_ppo_sync.py
    看主链路 fit() / step()，知道一个训练步发生了什么
    经典版可辅助看 trainer/main_ppo.py + trainer/ppo/ray_trainer.py
    ↓
第 3 站：single_controller/base/decorator.py
        + single_controller/ray/base.py
    理解 @register 与 dispatch / collect 调度
    ↓
第 4 站：workers/engine/base.py + workers/engine/fsdp/
    理解训练引擎如何算 logprob / 更新参数 / 保存权重
    ↓
第 5 站：workers/rollout/
    理解 vLLM / SGLang / TensorRT-LLM / HF 如何生成 response
    ↓
第 6 站：trainer/ppo/core_algos.py
    理解 PPO / GRPO / REMAX 等优化算法
    ↓
第 7 站：utils/checkpoint/ + checkpoint_engine/
    理解容错恢复、权重保存、训练权重到推理引擎的同步
```

### 2.2 阅读时重点问 4 个问题

每读一个函数，都建议记录：

```text
1. 输入是什么？DataProto、TensorDict、KVBatchMeta，还是普通 dict？
2. 输出是什么？会返回给 Driver，还是写入 TransferQueue？
3. 在哪个进程执行？Driver 还是 Ray Worker？
4. 张量是否真的经过 Driver？还是只传轻量元数据？
```

比如读 `compute_log_prob` 时，不要只看数学公式，还要问：

```text
谁调用它？
传入的是 DataProto 还是 KVBatchMeta？
它是在 actor worker 上执行吗？
结果写回哪里？
是否通过 TransferQueue 传递？
```

## 3. 顶层目录功能地图（仓库根）

| 目录/文件 | 用途 | 新手是否要读 |
|-----------|------|--------------|
| `verl/` | **核心源码**，本文重点 | 必读 |
| `examples/` | 各类训练脚本示例（`*.sh` + 配置），是跑起来的入口 | 强烈建议，先跑通再读码 |
| `tests/` | 单测 + 集成测试，看用法 / 边界的好材料 | 选读，可当“可运行文档” |
| `docs/` | 官方 rst/md 文档 | 选读 |
| `scripts/` | 模型转换、辅助脚本 | 用到再看 |
| `docker/` | 镜像与依赖环境 | 部署时看 |
| `my_docs/` | 本套中文源码解读（你正在看） | 必读 |
| `pyproject.toml` / `setup.py` / `requirements*.txt` | 打包与依赖 | 装环境时看 |

### 3.1 为什么建议先看 `examples/`

`examples/` 会告诉你：

- 用哪个训练入口。
- 用哪个模型。
- 用哪个 rollout 后端。
- actor / critic / ref / reward 怎么配置。
- batch size、prompt 长度、response 长度怎么设置。
- FSDP / Megatron / vLLM / SGLang 参数如何传入。

阅读 example 的目标不是研究 shell 语法，而是建立这条映射：

```text
脚本参数 / Hydra 配置
        ↓
trainer 初始化
        ↓
worker 创建
        ↓
训练循环中的具体方法调用
```

## 4. `verl/` 核心源码逐目录详解

### 4.1 顶层关键文件

| 文件 | 作用 |
|------|------|
| `protocol.py` | **最重要的数据结构文件**。定义 `DataProto`，统一封装 batch 张量、非张量数据和 `meta_info`，支持 `chunk` / `concat` / `select` / `union` / `to(device)` 等操作，是 Driver ↔ Worker 之间的“数据信封”。第一站必读。 |
| `base_config.py` | 配置基类，处理 dataclass 与 Hydra / OmegaConf 的桥接。追配置默认值和类型时会用到。 |
| `__init__.py` | 包初始化文件，可能包含环境兼容、后端补丁或包级导出逻辑。普通新手可后看。 |
| `py.typed` | PEP 561 类型标记文件，表示该包可被类型检查工具识别。无需重点阅读。 |

### 4.2 `trainer/` —— 编排层（Driver / Trainer，主链路在这）

`trainer/` 负责控制流程，而不是亲自做所有重计算。可以把它理解成“导演”：决定先 rollout，再算 reward，再更新 actor / critic。

| 文件/目录 | 作用 |
|-----------|------|
| `main_ppo.py` | 经典 HybridFlow PPO 入口，使用 `RayPPOTrainer`。虽然部分链路已被新实现替代，但逻辑直观，适合入门理解传统 PPO 流程。 |
| `main_ppo_sync.py` | **现行主链路**，核心类是 `PPOTrainer`，基于 `TransferQueue`、`ReplayBuffer`、`KVBatchMeta` 的同步 / 异步数据链路。重点看 `fit()`、`step()`、`init_workers()`。 |
| `main_eval.py` | 离线评测入口，用于生成结果并计算评估指标或 reward。 |
| `main_generation_server.py` | 独立 generation server 入口，用于启动生成服务并对 prompt 数据集生成响应。 |
| `sft_trainer.py` | SFT 训练器，基于不同 engine 后端执行监督微调。 |
| `sft_trainer_ray.py` | 实验性 Ray 版 SFT trainer，使用 single-controller 风格。 |
| `config/` | **Hydra YAML 配置目录**，例如 `ppo_trainer.yaml`。actor、critic、rollout、资源、优化器、batch size 等超参都在这里声明。 |
| `distillation/` | 蒸馏训练相关逻辑。新手可以后看。 |
| `ppo/` | PPO / GRPO / REMAX 等 RL 算法编排与核心算法目录。 |

#### 4.2.1 `trainer/ppo/` 重点文件

| 文件 | 作用 |
|------|------|
| `ray_trainer.py` | 经典 Ray PPO trainer 主体，包含老链路中的 worker 初始化、rollout、logprob、reward、advantage、actor / critic update 等流程。 |
| `core_algos.py` | **优化算法核心**。包括 advantage、KL penalty、policy loss、value loss、PPO / GRPO / REMAX 等算法实现。 |
| `metric_utils.py` | 训练指标统计，例如 reward、KL、loss、长度、吞吐等。 |
| `reward.py` | reward 计算编排。 |
| `rollout_corr_helper.py` | rollout correction 相关逻辑，涉及重要性采样、策略偏移修正、拒绝采样等。 |
| `utils.py` | PPO trainer 通用工具，例如 `Role` 角色枚举、配置辅助等。 |
| `padding_utils.py` | padding / unpadding 辅助工具。 |
| `prefix_grouper_utils.py` | prefix 分组相关工具，通常用于优化 rollout 或 batch 组织。 |

#### 4.2.2 新手怎么读 `main_ppo_sync.py`

不要从头到尾逐行读。建议按这个调用链跳读：

```text
main / run
    ↓
PPOTrainer.__init__
    ↓
init_workers
    ↓
fit
    ↓
step
    ↓
_generate_rollout / sample
    ↓
_compute_old_log_prob
    ↓
_compute_ref_log_prob
    ↓
_compute_advantage
    ↓
_update_critic
    ↓
_update_actor
    ↓
_checkpoint / sync weights
```

重点关注：

- 哪些操作发生在 Driver。
- 哪些操作被派发到 Worker。
- 哪些 batch 是 `DataProto`。
- 哪些 batch 只通过 `KVBatchMeta` 传递。
- `ReplayBuffer` 存的是张量还是元数据。

### 4.3 `single_controller/` —— 分布式调度层（dispatch / collect）

`single_controller/` 的目标是让 Driver 像写单机代码一样调用：

```text
wg.compute_log_prob(batch)
wg.update_actor(batch)
wg.generate_sequences(batch)
```

底层自动完成：

```text
切分 batch
    ↓
分发到多个 Ray actor
    ↓
在多张 GPU / 多个 rank 上执行
    ↓
收集结果
    ↓
返回给 Driver 或写入队列
```

| 文件 | 作用 |
|------|------|
| `base/decorator.py` | **`@register(dispatch_mode=...)` 装饰器**与各预定义 dispatch 模式，如 `DP_COMPUTE_PROTO`。这是理解调度机制的钥匙。 |
| `base/worker.py` | Worker 基类，负责读取 `WORLD_SIZE` / `RANK`，建立通信组和基础运行环境。 |
| `base/worker_group.py` | WorkerGroup 抽象，`_bind_worker_method` 会把 worker 方法代理到 Driver 上。 |
| `ray/base.py` | Ray 实现，包含 `RayWorkerGroup`、`ResourcePoolManager`、PlacementGroup 资源管理和远程方法生成逻辑。 |

核心流程可以理解为：

```text
Driver 调用 wg.compute_log_prob(batch)
        ↓
WorkerGroup 代理方法
        ↓
dispatch_fn 切分 batch
        ↓
Ray actor method.remote()
        ↓
collect_fn 聚合结果
```

---

### 4.4 `workers/` —— 执行层（重计算都在这）

`workers/` 是真正执行训练、推理、reward 的地方。可以把它理解成“演员”：trainer 下达任务，worker 在 GPU 上完成计算。

| 目录/文件 | 作用 |
|-----------|------|
| `engine_workers.py` | **核心 worker 文件之一**。封装 Actor / Critic / Ref / Reward 等角色 Worker，并把角色逻辑和训练 engine 接起来。 |
| `config/` | worker 侧配置 dataclass。追 actor、critic、rollout、optimizer、checkpoint 参数时会用到。 |
| `engine/` | 训练引擎抽象与不同训练后端实现。 |
| `rollout/` | 生成推理后端目录，负责生成 response。 |
| `reward_manager/` | 奖励管理：`naive.py` / `batch.py` / `dapo.py` / `prime.py` + `registry.py` 等。 |
| `utils/` | worker 侧工具函数。 |

#### 4.4.1 `workers/engine/` —— 训练后端

| 文件/目录 | 作用 |
|-----------|------|
| `engine/base.py` | 训练引擎抽象接口，定义模型初始化、forward / backward、train batch、infer batch、save / load checkpoint 等能力。 |
| `engine/fsdp/` | **FSDP / FSDP2 后端**，最常用，新手建议先看。 |
| `engine/megatron/` | Megatron-Core / 3D 并行后端。 |
| `engine/automodel/` | HuggingFace AutoModel 风格后端。 |
| `engine/torchtitan/` | TorchTitan 后端。 |
| `engine/veomni/` | VeOmni 多模态 / omni-modal 后端。 |
| `engine/mindspeed/` | Ascend / MindSpeed / NPU 相关后端。 |

新手只需要先记住：

```text
trainer 不直接操作模型细节
worker 调用 engine
engine 决定模型如何 forward / backward / update / checkpoint
```

#### 4.4.2 `workers/rollout/` —— 生成推理后端

| 文件/目录 | 作用 |
|-----------|------|
| `rollout/base.py` | rollout 基类，定义生成接口。 |
| `rollout/hf_rollout.py` | HuggingFace 本地 rollout，适合理解基础生成流程或调试。 |
| `rollout/naive/` | 朴素 rollout 实现，适合新手理解和排查问题。 |
| `rollout/vllm_rollout/` | **vLLM rollout 后端**，常用高性能生成方案。 |
| `rollout/sglang_rollout/` | SGLang rollout 后端。 |
| `rollout/trtllm_rollout/` | TensorRT-LLM rollout 后端。 |
| `rollout/llm_server.py` | LLM server 管理逻辑。 |
| `rollout/replica.py` | rollout replica 管理。 |
| `rollout/schemas.py` | rollout 请求 / 响应 schema。 |

如果你关心“模型是怎么生成 response 的”，重点看这里。

### 4.5 `experimental/` —— 实验性链路与 Agent Loop

`experimental/` 下包含一些新链路或实验性能力。新手不建议一开始深入，但 `main_ppo_sync.py` 的部分同步 / 异步生成调度会依赖这里。

| 目录 | 作用 |
|------|------|
| `agent_loop/` | **AgentLoop 核心**。包括 `agent_loop.py`、`single_turn_agent_loop.py`、`tool_agent_loop.py`、`tool_parser.py`，用于单轮 / 多轮 / 工具调用式 rollout。 |
| `reward_loop/` | 异步 reward 计算环。 |
| `fully_async_policy/` | 全异步 policy 训练实验。 |
| `one_step_off_policy/` | 一步 off-policy 训练实验。 |
| `teacher_loop/` | teacher model / teacher loop 相关实验。 |
| `separation/` | trainer / rollout 分离实验。 |

建议：先掌握 `trainer/`、`workers/`、`single_controller/`、`protocol.py`，再看 `experimental/`。

### 4.8 `checkpoint_engine/` —— 高速权重同步引擎

`checkpoint_engine/` 负责训练权重到推理引擎之间的高速同步，以及不同通信后端下的 checkpoint / weight update 能力。

| 文件 | 作用 |
|------|------|
| `base.py` | checkpoint engine 抽象。 |
| `nccl_checkpoint_engine.py` | NCCL 后端，常见于 CUDA GPU 场景。 |
| `hccl_checkpoint_engine.py` | HCCL / Ascend 后端。 |
| `nixl_checkpoint_engine.py` | NIXL 后端。 |
| `mooncake_checkpoint_engine.py` | Mooncake 后端。 |
| `kimi_checkpoint_engine.py` | Kimi 风格 checkpoint engine。 |

它解决的问题可以理解为：

```text
actor 训练权重更新
    ↓
保存 / 同步 / 广播
    ↓
rollout engine 加载新权重
    ↓
下一轮 rollout 使用更新后的策略
```

如果你只想理解 PPO 算法，可以后看；如果你遇到“训练后 rollout 没更新权重”，就需要看这里。

## 6. 新手最容易混淆的概念

### 6.1 `trainer`、`worker`、`engine` 的区别

```text
trainer 是导演：决定训练流程怎么走。
worker 是演员：在 Ray actor / GPU 上真正执行计算。
engine 是演员手里的训练设备：决定模型如何 forward / backward / update / checkpoint。
rollout backend 是生成 response 的推理引擎。
```

### 6.2 `actor`、`critic`、`ref`、`reward` 的区别

| 角色 | 含义 |
|------|------|
| actor | 要训练的策略模型，用来生成 response，并通过 PPO / GRPO 更新。 |
| critic | value model，估计状态 / token 的 value，用于 advantage 计算。 |
| ref | reference policy，用于计算 KL penalty，防止 actor 偏离初始模型太远。 |
| reward | 奖励模型或规则打分函数，用于评价 response 好坏。 |

### 6.3 `rollout` 和 `actor` 的区别

- `actor` 是要训练的策略模型。
- `rollout` 是用当前策略模型生成 response 的过程或推理服务。
- 有些配置下 actor 和 rollout colocate，有些配置下二者分离。
- rollout engine 需要定期同步 actor 的新权重，否则生成策略会落后。

### 6.4 `DataProto` 和 `TensorDict / TransferQueue` 的区别

| 概念 | 作用 |
|------|------|
| `DataProto` | 经典链路中显式传递 batch 的容器。 |
| `TensorDict` | 更灵活的数据容器，支持 nested tensor / 变长序列。 |
| `TransferQueue` | 新链路的数据面，张量不经过 Driver。 |
| `KVBatchMeta` | 只包含 key / tags 的轻量元数据句柄。 |

一句话：

```text
DataProto 偏“把数据打包传走”
TransferQueue + KVBatchMeta 偏“真实张量留在队列里，只传索引和句柄”
```

### 6.5 `main_ppo.py` 和 `main_ppo_sync.py` 的区别

| 文件 | 特点 |
|------|------|
| `main_ppo.py` | 经典 HybridFlow PPO 链路，逻辑更直观，适合新手先建立训练流程。 |
| `main_ppo_sync.py` | 现行主链路，引入 `TransferQueue`、`ReplayBuffer`、`KVBatchMeta`，性能设计更复杂。 |

建议：

```text
先用 main_ppo.py / ray_trainer.py 理解传统 PPO 结构
再用 main_ppo_sync.py 理解当前高性能链路
```

## 7. 新手实操建议路径

1. **先跑起来**
   - 在 `examples/` 找一个 GRPO / PPO 的 `*.sh`，例如 GSM8K、小模型或本地可运行配置。
   - 先建立“看得见”的反馈，不要一开始只读代码。

2. **打日志 / 断点读 `step()`**
   - 在 `trainer/main_ppo_sync.py` 的 `step()` 各阶段打日志或断点。
   - 对照 [01-核心运行流程.md](01-核心运行流程.md) 看数据怎么流。

3. **顺藤摸瓜**
   - 每遇到一个 `wg.xxx(batch)` 调用，就去对应 worker 找同名方法实现。
   - 看它的 `@register(dispatch_mode=...)`，理解数据怎么被切分和收集。

4. **算法单独攻**
   - 把 `trainer/ppo/core_algos.py` 配合 [03-优化算法.md](03-优化算法.md) 单独读一遍。
   - 不要把算法细节和分布式调度混在一起理解。

5. **遇到工具函数再查 `utils/`**
   - `utils/` 是工具箱，不是主线剧情。
   - 遇到 `TensorDict`、checkpoint、tokenizer、reward_score、vLLM 辅助函数时再查。

6. **用 tests 当文档**
   - `tests/` 里的单测和集成测试往往能告诉你某个函数“应该怎么用”。
   - 当你看不懂某个类时，搜索它在 `tests/` 中的用法通常很有效。
