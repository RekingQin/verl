# 13 · 异步训练方案对比（主链路 vs one_step_off vs fully_async）

> 返回索引：[README.md](README.md)
> 关联阅读：[01-核心运行流程.md](01-核心运行流程.md)、[10-Ray串联机制详解.md](10-Ray串联机制详解.md)、[11-算法配置与跨Worker数据流转.md](11-算法配置与跨Worker数据流转.md)
> 源码：`verl/trainer/main_ppo.py` + `verl/trainer/ppo/v1/`（主链路，含三种 V1 模式）、`verl/experimental/one_step_off_policy/`、`verl/experimental/fully_async_policy/`
> 版本提示：主库已内置 **V1 三种 trainer 模式**（`trainer.v1.trainer_mode`）：`sync`（= 原 `main_ppo_sync.py`）、`colocate_async`（kimi-1.5 风格，colocate + partial rollout）、`separate_async`（AReaL 风格，分离 + partial rollout）。`experimental/fully_async_policy` 与 `one_step_off_policy` 仍保留为独立实验入口，设计思路与 V1 的 `separate_async` 一致。

本篇从**设计架构 / 运行流程 / 算法实现 / 配置 / 数据流 / 性能与效果**六个维度，对比同步方案与各异步方案。

---

## 13.0 一句话定位

| 方案 | 一句话 | 异步程度 |
|------|--------|----------|
| **V1 sync**（`PPOTrainerSync`，默认） | actor 与 rollout colocate 同卡，严格 on-policy，rollout→train 串行 | 0（同步） |
| **V1 colocate_async**（`PPOTrainerColocateAsync`） | colocate + **partial rollout**（kimi-1.5 风格），流式生成被训练打断后可续跑 | 可调（流式/partial） |
| **V1 separate_async**（`PPOTrainerSeparateAsync`） | 训练/rollout **彻底分离** + partial rollout（AReaL 风格），`parameter_sync_step` 控制同步频率 | 可调（多步/partial） |
| **one_step_off_policy**（experimental） | 资源隔离 + 生成/训练**重叠一步**，本步训练用上一步参数生成的样本 | 固定 1 步 |
| **fully_async_policy**（experimental） | Trainer/Rollouter **彻底拆成两个 Ray actor**，经 MessageQueue 流式生产消费，0.x~多步可调 | 可调（流式/多步/partial） |

共同动机：colocate 同步下，**rollout 长尾样本拖慢整步**（DAPO 32B 中 rollout 占~70%），加资源也压不下长尾时间，GPU 大量空转。异步方案用"生成与训练 overlap"来填这段空闲。

---

## 13.1 主链路（基线）回顾

- **架构**：`hybrid_engine=True`，actor/critic/ref/rollout 共享 `global_pool` colocate 同卡（见 [10](10-Ray串联机制详解.md) §10.8）。
- **流程**：`generate_sequences → compute_log_prob → (ref/values) → advantage → update_critic → update_actor → update_weights`，**严格串行 + 同步屏障**，本步训练数据必来自本步 rollout（on-policy）。
- **数据面**：v0 经典版（`main_ppo_v0.py`）用 `DataProto` chunk/concat；V1 主链路（`main_ppo.py` + `ppo/v1/`）用 TransferQueue + ReplayBuffer（零拷贝）。
- **瓶颈**：rollout 与 train 同卡分时，长尾期间训练资源闲置。

## 13.2 one_step_off_policy（一步重叠流水线）

> 作者 meituan；参考 AReaL / Asynchronous RLHF。核心类 `OneStepOffRayTrainer`（`experimental/one_step_off_policy/ray_trainer.py:49`），继承 `SeparateRayPPOTrainer`。
> 状态：仍为独立实验入口；其"生成与训练 overlap"的核心理念已被 V1 的 `colocate_async` / `separate_async` 模式吸收（见 13.1 版本提示）。

### 设计架构
- **关键开关 `hybrid_engine=False`**（ray_trainer.py:88 `assert not self.hybrid_engine`）：actor 与 rollout **不再 colocate**，而是**资源隔离**——
  - 训练资源：`trainer.nnodes × trainer.n_gpus_per_node`
  - 生成资源：`rollout.nnodes × rollout.n_gpus_per_node`（专用）
- WorkerGroup 分离：`actor_wg`（训练）+ rollout（经 `LLMServerManager` + `AgentLoopManager`，仅 async server 模式）。critic/ref/rm 各自 WG。

### 运行流程：一步 overlap（ray_trainer.py:265~408）
```
continuous_iterator = _create_continuous_iterator()        # 跨 epoch 连续迭代器
batch_future = create_task(_async_gen_next_batch(...))      # 先发起 step1 的异步生成
while batch_future:
   fit_step:
     batch, batch_future_prev = await _fit_generate:
        batch = await batch_future            # ① 等"上一步"生成结果
        _fit_update_weights()                 # ② actor→rollout 参数同步
        batch_future = create_task(_async_gen_next_batch(...))  # ③ 立即发起"下一步"生成(不等)
     # ④ 当前 batch 走训练链路, 与③的生成 overlap
     compute_reward → compute_log_prob → ref → critic → advantage → update_critic → update_actor
```
关键：`_async_gen_next_batch`（:206）用 `asyncio.create_task` 把生成做成 future（`GenerationBatchFuture`），**step N+1 的生成与 step N 的训练并行**。每个 `await asyncio.sleep(0)` 让出事件循环，保证后台生成持续推进。

### 算法实现
- **one-step-off**：本步训练样本由**上一参数版本**生成，天然 off-policy 一步。
- **PPO 正确性**：用 rollout log_probs 做重要性采样，默认 `bypass_ppo_clip`（README §PPO Correctness）。
- 支持的 adv estimator：GRPO / GRPO_PASSK / RLOO / RF++ / OPO / GPG 等（**不含 GAE/PPO-critic 的强同步配方**为主）。

### 参数同步
- **NCCL collective broadcast**（ray.util.collective）：actor 与 rollout 的 worker 组成一个 `actor_rollout` 通信组，逐 tensor `full_tensor()→broadcast(src_rank=0)`，rollout 端 `load_weights`。README 实测延迟 <300ms，几乎可忽略。

### 配置要点
```bash
actor_rollout_ref.hybrid_engine=False
trainer.nnodes / trainer.n_gpus_per_node     # 训练资源
rollout.nnodes / rollout.n_gpus_per_node     # 生成资源(独立)
# 约束: rollout.n 能整除 train GPU 总数, 或 rollout.n*train_batch_size 能被其整除
```
调参核心指标 `wait_prev_gen`（未被 overlap 掉的等待时间）：高且序列均匀→加生成资源；高且长尾→优化停止策略。

### 性能与局限
- DAPO 32B：FSDP2 +23%、Megatron +40%（README 实验表）。
- **局限**：强制恰好 1 步异步，不灵活；**仍不能完全消除长尾**（一步内仍要等该步最长样本）。

## 13.3 fully_async_policy（完全解耦 + 流式 + 多步异步）

> 作者 meituan；参考 AReaL / Magistral / StreamRL / AsyncFlow。
> 状态：仍为独立实验入口；其"双 actor 解耦 + 流式 + partial rollout"的设计已被 V1 的 `separate_async` 模式正式化（`PPOTrainerSeparateAsync`，trainer/ppo/v1/trainer_separate_async.py，内部复用 `experimental/separation` 的 `DetachActorWorker`）。

### 设计架构：四组件 + 双 actor 并发
```
FullyAsyncTaskRunner (@ray.remote, fully_async_main.py:35)
   ├─ FullyAsyncTrainer  (@ray.remote actor)   训练资源 trainer.*
   ├─ FullyAsyncRollouter(@ray.remote actor)   生成资源 rollout.*
   ├─ MessageQueue       (@ray.remote actor)   双端缓冲(deque)
   └─ ParameterSynchronizer (checkpoint-engine NCCL)
   _run_training_loop: rollouter.fit.remote() 与 trainer.fit.remote() 同时跑, ray.wait 监控
```
与 one_step_off 的根本差异：**Trainer 和 Rollouter 是两个独立 Ray actor、各跑各的 `fit()` 事件循环**，不再由单一 Driver 顺序编排；二者通过 **MessageQueue** 解耦（生产者-消费者）。

### 运行流程
- **Rollouter**（fully_async_rollouter.py）：**逐样本**流式生成，`put_sample` 进 MessageQueue；生产速度受**新鲜度**约束（`staleness_samples >= max_required_samples` 则 `paused`）。
- **MessageQueue**（message_queue.py:27）：Ray actor 封装 `deque(maxlen)`，`asyncio.Condition` 协调；满则丢最旧样本。最小传输单位 = **单个 sample**。
- **Trainer**（fully_async_trainer.py:412 `fit_step`）：
  ```
  while True: fit_step:
    batch = _get_samples_from_queue()      # 攒够 require_batches*ppo_mini_batch_size 个样本
    reward → log_prob → ref → critic → advantage → update_critic → update_actor
    _fit_update_local_step()               # 本地步+1
    _fit_update_weights()                  # 每 trigger_parameter_sync_step 次本地更新 → 同步一次参数
  ```
  即 Trainer 连续做 `trigger_parameter_sync_step` 次本地更新才与 Rollouter 同步一次参数（`current_param_version += 1`）。

### 四种模式（README §模式支持）
| 模式 | 参数组合 | 特征 |
|------|----------|------|
| ① on-policy pipeline | `trigger=1, staleness=0` | 等价单步同步，仍有长尾空闲 |
| ② stream off-policy | `trigger>1, staleness=0` | 同步流式，一次生成更多、空闲更低 |
| ③ async + staleness | `trigger≥1, staleness>0, partial=False` | 允许旧样本，提前多生成；需等进行中任务结束 |
| ④ async + partial rollout | `trigger≥1, staleness>0, partial=True` | 同步时**打断**进行中生成(sleep)，同步后**续跑**(resume)，几乎无等待 |

### 算法实现
- **`use_rollout_log_probs=True`**：`old_log_prob` 默认由 **rollout** 计算（保证 IS 正确性），不由 trainer 重算。
- **`rollout_correction.bypass_mode`**：默认 True（直接用 rollout log prob）；设 False + Rollout IS → **近似 AReaL 的 Decoupled PPO**（缓解后期 response 长度不稳定）。
- **staleness_threshold**：`max_required_samples = required_samples*(staleness+1)*trigger`（rollouter.py:533）。0=同步；>0=异步可用旧样本（建议<1）；rollout 够快时 staleness=1 ≈ one_step_off。

### 参数同步
- **checkpoint-engine NCCL**（参考 Moonshot checkpoint-engine）：`checkpoint_manager.update_weights(global_steps=param_version)`（trainer.py:511）。消融实测：30B 单步同步 15.76s→4.38s（开 ckpt-engine），235B 58.57s→23.70s。

### 配置要点
```bash
data.train_batch_size=0          # 不生效
data.gen_batch_size=1            # 流式
rollout.total_rollout_steps=...  # 总样本数 = train_batch_size*step 对齐 colocate
async_training.require_batches            # 一次攒几个 mini_batch 再训
async_training.trigger_parameter_sync_step# 多少次本地更新后同步一次参数
async_training.staleness_threshold        # 新鲜度(0同步, >0异步)
async_training.partial_rollout            # 打断/续跑
async_training.use_trainer_do_validate    # 用 trainer 侧 hybrid WG 做验证
```

### 性能与效果
- 128 卡 7B：**2.35x~2.67x**；30B：1.7x；多轮工具：1.55x~1.6x。
- 收益拆解：stream ~1.6x，叠加 staleness + partial_rollout → 2.35x。
- 效果：精度基本不掉（acc/mean 与 colocate 接近，部分更高）；staleness 越大越快，但过大致后期不稳定（建议 <1）。
- 关键指标：`trainer/idle_ratio`、`rollouter/idle_ratio`（据此调资源配比）、`stale_samples_processed`、`partial_ratio`。

## 13.3b critic / ref / reward 在分离架构里怎么放（关键澄清）

异步方案只把 **rollout** 拆出去独占资源，**critic、ref 仍与训练侧 actor colocate 在 `trainer_pool`**，reward 挂在 rollout 那条流式线上。依据 `separation/utils.py` 与 `separation/ray_trainer.py`：

```python
# create_resource_pool_manager (separation/utils.py:37)
training_roles = [Role.Actor, Role.ActorRollout, Role.Critic, Role.RefPolicy]
trainer_pool = [trainer.n_gpus_per_node]*trainer.nnodes
for role in training_roles: mapping[role] = "trainer_pool"   # Actor/Critic/Ref 同池
```

| 角色 | 归属 | 说明 |
|------|------|------|
| **Rollout** | 独占 `rollout.*`（rollout.nnodes×n_gpus_per_node） | 唯一被隔离出去；经 LLMServerManager/AgentLoopManager（fully_async 里是独立 Rollouter actor）|
| **Actor(训练)** | `trainer_pool` | 训练侧 |
| **Critic** | `trainer_pool`，与 actor **colocate** | `_create_critic_class` 写入同池，`create_colocated_worker_cls` 融合；分时 |
| **Ref** | `trainer_pool`，与 actor **colocate** | 同上 |
| **Reward** | `RewardLoopManager` | 函数式 reward(`use_rm=False`)随 rollout **流式打分**(`reward_loop_worker_handles`→AgentLoopManager)，不占训练 WG；reward **模型**(`use_rm=True`)才另占 reward 池 |

要点：被异步拆分的只有"长尾瓶颈所在的 rollout"；critic/ref 这类训练侧前反向算子仍跟 actor 挤在训练池 colocate，分时复用；reward 不是独立训练组，而是挂在 rollout 流式线上（`enable_agent_reward_loop = not use_rm or reward模型有独立池`）。

## 13.4 六维度横向对比

| 维度 | V1 sync | V1 colocate_async | V1 separate_async | one_step_off（exp） | fully_async（exp） |
|------|---------|-------------------|-------------------|---------------------|--------------------|
| **架构** | colocate 单 Driver | colocate 单 Driver | 分离（standalone rollout），单 Driver | 资源隔离, 单 Driver+asyncio | Trainer/Rollouter 双 actor + MQ |
| **hybrid_engine** | True(同卡) | True(同卡) | 分离（`rollout.nnodes` 独立资源） | False(分卡) | False(分卡) |
| **资源** | 全角色共享 global_pool | 全角色共享 global_pool | trainer.* + 独立 rollout.* | trainer.* / rollout.* 两组 | trainer.* / rollout.* 两组 |
| **生成/训练关系** | 串行(同步屏障) | 流式 + 打断/续跑 | 流式 + 打断/续跑 | overlap 一步 | 完全解耦, 流式并发 |
| **partial rollout** | 无 | **支持**(abort/resume) | **支持**(abort/resume) | 无 | 支持(sleep/resume) |
| **异步步数** | 0 | 流式 | 多步（`parameter_sync_step`） | 固定 1 | 0.x ~ 多步(可调) |
| **on/off-policy** | on-policy | on-policy 为主 | off-policy（跨参数版本，`max_off_policy_threshold`） | off-by-1 | 可调(staleness) |
| **数据载体** | TransferQueue + ReplayBuffer | TransferQueue + ReplayBufferAsync | TransferQueue + ReplayBufferAsync | DataProto + GenerationBatchFuture | RolloutSample 经 MessageQueue(单样本) |
| **调度** | Driver 顺序 RPC | Driver asyncio 流水线 | Driver asyncio 流水线 | Driver asyncio.create_task 重叠 | 两 actor 独立事件循环 |
| **参数同步** | colocate in-process/CUDA IPC | colocate in-process/CUDA IPC | checkpoint-engine NCCL（非 naive 后端） | NCCL collective.broadcast | checkpoint-engine NCCL |
| **old_log_prob** | actor 重算(可 bypass) | actor 重算(可 bypass) | actor 重算（`DetachActorWorker` CPU save/restore 支持 Decoupled PPO） | rollout log_probs(bypass_ppo_clip) | rollout 算(use_rollout_log_probs) |

| **精度影响** | 基准 | 基准 | 基本无 | 基本无 | 基本无(staleness<1) |
| **复杂度/灵活性** | 最简 | 中 | 中高 | 中 | 高(模式多、可调多) |
| **入口** | `main_ppo.py` + `trainer_mode=sync` | `main_ppo.py` + `trainer_mode=colocate_async` | `main_ppo.py` + `trainer_mode=separate_async` | `one_step_off_policy.async_main_ppo` | `fully_async_policy.fully_async_main` |

## 13.5 数据流差异图

```
V1 sync(同步):
  Dataset → [Driver] generate → logprob → adv → update → update_weights → 下一步
            └────────── 同一进程顺序, 同步屏障, 张量经 TransferQueue ──────────┘

V1 colocate_async(colocate + partial):
  [Driver] gen(流式, 边生成边攒 batch) ── 训练打断 ──► abort_replicas
  → update_weights(同卡 CUDA IPC) → resume_generation_replicas(续跑未完成生成)
  (rollout 长尾不再阻塞整步, 训练与未完成生成重叠)

V1 separate_async(分离 + partial):
  [Driver] trainer(actor/critic/ref 训练) ── update_weights(checkpoint-engine NCCL, 每 parameter_sync_step 次)
                 └── standalone rollout(独立资源池, LLMServerManager) 持续流式生成
  (训练与生成彻底解耦; Decoupled PPO 经 DetachActorWorker 的 CPU save/restore)

one_step_off(重叠一步):
  step N:   train(用 N-1 参数生成的 batch) ──────┐
  step N:   gen(N+1 batch, asyncio 后台)  ───────┤ overlap
            await prev_gen → update_weights(NCCL broadcast) → 攒下一步
            (单 Driver 用 future 把"生成"与"训练"并行)

fully_async(完全解耦流式):
  Rollouter(独立actor): 逐样本生成 ──put_sample──► MessageQueue(deque)
                            ▲ staleness 控速; partial 可打断/续跑      │ get_sample
  ParameterSynchronizer ◄── 每 trigger 次本地更新同步一次(ckpt-engine NCCL)
                                                                       ▼
  Trainer(独立actor): 攒 require_batches*mini_bsz → 训练 → param_version+1
```

## 13.6 选型建议

- **要严格 on-policy、稳定优先、规模小** → `trainer_mode=sync`（默认），或 fully_async 模式①。
- **想要低成本 partial rollout（长轨迹不被训练打断）** → `trainer_mode=colocate_async`（V1 内置，改配置即用）。
- **大规模、长尾严重、训练/生成资源可分离** → `trainer_mode=separate_async`（V1 内置，`parameter_sync_step` 控制同步频率），加速接近 fully_async。
- **想在 experimental 中深度调参（staleness / 背压策略）** → one_step_off（一步 overlap）或 fully_async 模式③/④（staleness>0 + partial_rollout），加速最大（2x+）。

各方案算法内核（core_algos 的 adv/policy loss）完全共用，差异集中在**资源拓扑、生成/训练的并发编排、参数同步方式、off-policy 修正（Rollout IS / Decoupled PPO）**。详见 `trainer/README.md` 与各自 `README`。
